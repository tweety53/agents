Why picked

1. Defect class: an ordering or first-pick test whose fixture rows sort the same under the tested key and under a competing one (an id tie-break, insertion order), so it cannot tell the two apart and passes by chance. 2. The test-sanity slot's "Can it fail?" lens lists tautologies, configured mocks, assertions on the fixture, empty tests and dead paths, but nothing about fixture data that does not discriminate between keys: the before quote is that whole lens. 3. It generalises to every sorted list, first-by, latest-by or tie-break test in any language and layer; the test landed in round 3's fix (f5ff3bce, panel-fix-3), and the test-sanity slot reviewed it in rounds 5 and 6 and the mutation slot in rounds 4 to 6 without raising it, until round 7's mutation slot found `order by p.id` survived (the random UUIDs happened to sort as the names did), and the fix (bfadad68) had to read the ids back in Postgres order to build data where the keys disagree. 4. It states a principle (an ordering test's data must order differently under every competing key), not a special case of this task.

    - **Can it fail?** Would the test fail if the behaviour it names broke? A tautology
      (asserting a value against itself, or against the same expression the code computes),
      an assertion on a mock or stub the test itself configured, an assertion on the fixture
      or the test's own input, a test that asserts nothing, and a test whose assertions sit
      on a path that never runs (a swallowed panic, an early return, a skipped table row,
      an unawaited promise) all fail this lens.
      An ordering, first-by or tie-break test whose fixture rows sort the same under a
      competing key — the id, insertion order, another column — fails it too: the test
      cannot tell the key under test from the competing one, so a swap passes by chance.
