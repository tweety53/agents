Why picked

1. Defect class: a request path fetches a list and then reads each item's detail (or the same row again) in a loop, an N+1 the caller pays on every load, where one query returning the needed field would do. 2. The implementer instructions name no rule about the number of reads a path issues: engineering-principles.md's KISS reads "Choose the simplest construction that solves the problem actually in front of you." and a grep for N+1, round trip, once per and per item across engineering-principles.md, implement.md and sdd-dispatch.md finds nothing that applies; the per-item loop is the simplest construction, so KISS endorses it. 3. It generalises: the same run's panel raised F1 (one week_program row loaded up to three times in a single request) and F3 (a count call repeating the list's own total) besides this Critical, three call-efficiency findings on two layers and two languages, each costing a fix round. 4. It states a principle (a path's read count is constant in its data: fetch what a view needs in one read, never once per row), not a special case of this task.
