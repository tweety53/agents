Why picked

1. Defect class: a fallback taken on 'cannot reach it' also fires on 'it answered with an error', turning a refusal into a pass. 2. No rule covers it: the robustness principle reads "Be strict about what you emit and defensive about what you accept, fail fast on programmer error, degrade gracefully on environmental error, and make every failure observable.", and nothing says to separate unreachable from answered-badly before degrading. The implementer read a non-200 as environmental and skipped the UI-check read with a warning, and the failure-modes slot raised it as an Important that cost a fix round. 3. It generalises: every client error sentinel that callers branch on for an offline or journal fallback has the same shape — here the CLI's documented fallback trigger wraps non-200 statuses and unparseable bodies across its client methods. The same holds for any cache-or-network fallback, offline mode or fail-open guard in any language. 4. It is a principle, not a patch: degrade only on the condition the fallback was built for, and treat every other failure as a failure.
