Why picked

1. Defect class: a persisted state transition guards its source state in a read and then writes unconditionally, so two concurrent transitions from the same state both succeed. 2. The robustness principle covers emit/accept strictness, fail-fast and graceful degradation but names no rule for concurrent state changes, check-then-act or conditional writes; a grep for race, concurrent and compare-and-set across engineering-principles.md, implement.md and sdd-dispatch.md finds nothing that applies. 3. It generalises to every persisted state machine a backend writes — review, publish, invite accept, order or payment status — in any language. 4. It states a principle (put the source-state guard in the write itself), not a special case of this task.

Be strict about what you emit and defensive about what you accept, fail fast on
programmer error, degrade gracefully on environmental error, and make every failure
observable.
A state transition on shared persisted data puts its source-state check in the write
itself — a conditional update (`where state = <expected>`) or compare-and-set whose
zero-row result is a conflict — never a read followed by an unconditional write.
