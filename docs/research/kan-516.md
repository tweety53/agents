# Log unprefixed fixes in the store as `/flow <name>` fix runs — research notes

Source: KAN-516

Explored via `/flow-plan` on 2026-09-16 against `origin/main` at `ad45fa5`: the `/flow` router
(`skills/flow/SKILL.md`), the fix path (`skills/flow/implement.md` section 3), the state
transition table (`skills/flow-contracts/pipeline.md`), the store's run grouping and token
attribution (`stats/internal/store/runs.go`, `stats/internal/harvest/attribute.go`), the hook
installer (`setup.sh`, `hooks/`, `scripts/test-setup.sh`) and the two harnesses' hook contracts.
The operator's topic, from the ticket: problems found while testing are typed as plain messages,
without the `/flow kan-XXX` prefix, because that is more convenient — and the store then holds
almost nothing about those fixes. Every decision below is the operator's answer to a question this
session asked, or a routine call recorded with its rejected alternative.

## 1. What an unprefixed fix loses today

- **A store "run" is the set of stage marks sharing one session token** (`groupRuns`,
  `stats/internal/store/runs.go`). A `/flow <name> <fix>` run generates a fresh `mf-` token and
  marks `flow.document-fix`, `flow.sdd-tdd`, `flow.review-panel`, `flow.verify`,
  `flow.visual-verify`, `flow.stage-diff`, `flow.run-instructions` and `flow.write-in-progress`
  under it. A `/flow` run whose first stage is not `flow.kickoff` counts as one fix iteration
  (`FixIterations`).
- **Tokens, cost and wall-clock are attributed only inside stage windows** — the harvester binds
  the token found in the transcript to the session id, then assigns every transcript record to
  the open stage window containing its timestamp; a record outside every window "is silently not
  attributed" (`Attributor.Attribute`, `stats/internal/harvest/attribute.go`).
- **So a fix typed as a plain message makes no marks and leaves nothing behind**: no run row, no
  fix iteration, no dispatch rows, no findings, no task-count observation, no token or cost
  figures, no fix ordinal in `proposal.md`/`tasks.md`. The session does the work; the store
  records a session that went idle.
- **The fix path itself already exists.** Section **3. Documenting a fix, before implementing
  it** (`skills/flow/implement.md`) runs whenever the router reads `IN_PROGRESS` with an
  argument. The only thing missing is a router entry: **Reading the state**
  (`skills/flow/SKILL.md`) is entered by a `/flow` invocation and a plain message never reaches
  it.

## 2. Trigger and ceremony

- **Ceremony — the full fix run.** An unprefixed problem report runs exactly as
  `/flow <name> <message>` would: the document-fix planning pass with its where-should-it-go
  question, implementation, the review panel, verification and the handoff. Rejected: an inline
  fix wrapped in marks only (tokens and a fix iteration would land, but the planning pass, panel
  and verify records would not — a second, thinner kind of fix run the store cannot tell apart),
  and asking each time whether to run it as a fix (a click on every message, which is the
  convenience the ticket is about).
- **Trigger — change requests only.** A message that reports a problem or asks for a change to
  the change's code or artifacts is a fix run. A question, a discussion, or an unrelated task
  stays an ordinary turn. Rejected: every non-slash message, which would turn "why did you do
  that?" into a planning pass.
- **Ambiguity — ask once.** A message that reads either way is one **AskUserQuestion**, shape
  per **The shape** (`skills/flow-contracts/operator-prompts.md`): "**Run this as a fix of
  `<name>`?**" with **Yes** *(recommended)* and **No — ordinary turn**; silence takes Yes, and
  the fix run's handoff carries the ⚠ line. Rejected: treating doubt as an ordinary turn (the
  silent data loss the ticket describes) and treating doubt as a fix run (a planning pass over a
  question).
- **Cold sessions are not covered.** Only a session that already ran `/flow <name>` is in scope.
  A session opened in a change's worktree with no prior run, and a Jira key named in prose
  without the slash, both stay ordinary turns — each is a discovery mechanism of its own, and
  neither is the case the ticket reports.
- **The fix instructions are the verbatim message.** Nothing is paraphrased between the operator
  and the planning pass; the message is what `/flow <name> <message>` would have carried.
- **The state gate is the existing one.** The fix run starts only when `flow state get <name>`
  answers `IN_PROGRESS`. Any other state — `STARTED`, `FINISHED`, no state, a store that cannot
  be reached — makes the message an ordinary turn, never a wrong-state handoff: the operator
  invoked nothing, so there is no command to report a wrong state for.

## 3. Discovery — skill text plus a prompt hook

- **Two mechanisms, one rule.** The rule itself lives in the `/flow` skill (section 4). A
  `UserPromptSubmit` hook, `hooks/flow-active-change.py`, supplies the change name
  deterministically on every plain prompt, so the rule survives context compaction and a long
  session — the transcript file is append-only and keeps every mark the run made. Rejected:
  skill text alone (works on every harness but is lost the first time the skill's text falls out
  of the window) and a hook alone (the hook can name the change; it cannot classify a message,
  and the rule has to be readable by a session with no hook registered).
- **The hook derives the change from the transcript's last `/flow` mark.** Every
  `flow stage begin -command '/flow' … -session-token mf-<token> <name>` the run made is
  recorded verbatim in the session's transcript, and the resolved change name is the positional
  argument after the token — the shape `check-stage-mark-calls.sh` already enforces. The hook
  takes the last match of `flow stage begin -command '/flow' … -session-token mf-<token>
  <name>` in the file; `-command '/flow-plan'` and `-command '/flow-fast'` never match, since
  neither command has a fix run. Rejected: the last `/flow <arg>` command message (its argument
  is a Jira key or a description on a creating run, not the resolved name) and a store lookup by
  token (a store round-trip on every prompt, and the binding lands only after the harvester's
  next pass).
- **Transcript path.** Claude Code passes `transcript_path` in the hook's stdin JSON. ZCode's
  rollout for a session is `<rollout root>/model-io-sess_<session id>.jsonl`, the root
  `~/.zcode/cli/rollout` or `FLOW_ZCODE_ROLLOUTS_DIR` when set — the same variable the harvester
  reads (`DefaultZcodeRolloutRoot`, `stats/internal/harvest/rollout.go`), reused rather than a
  second name for the same directory. The hook reads `transcript_path` when present, else derives
  the rollout path from `session_id` in the payload or `CLAUDE_SESSION_ID` in the environment.
  The match is a regular expression over the raw file, so the JSON escaping of either format is
  irrelevant: the change name is matched as `[A-Za-z0-9._-]+`, which a kebab-case change name
  satisfies and an escaped quote or newline terminates.
- **Output shape.** The hook prints one JSON object,
  `{"hookSpecificOutput": {"hookEventName": "UserPromptSubmit", "additionalContext": "<line>"}}`,
  the `<line>` being `flow: this session's last /flow run marked change <name>. A plain message
  reporting a problem or asking for a change to it is a fix run of <name> — **A plain message at
  IN_PROGRESS** (skills/flow/SKILL.md).` — Claude Code's documented shape, and the
  `additionalContext` key is what ZCode's strict output schema injects. It prints nothing when
  the prompt starts with `/` (a command routes itself), when the transcript holds no `/flow`
  mark, or when the transcript cannot be read.
- **Fails open, like the existing hook.** Any malformed input, missing file or internal fault
  exits 0 with no output — the same contract as `hooks/enforce-agent-baseline.py`. A hook that
  supplies context must never be the reason a prompt is refused.
- **Harness coverage.** Claude Code and ZCode both support `UserPromptSubmit`; the installer
  links every file in `hooks/` into both harness directories already. Cursor has no hook layer,
  so there the rule runs on skill text alone. Registration stays the operator's paste, exactly as
  for the baseline hook: `setup.sh` prints the snippet and never edits `settings.json` or
  `config.json`.

## 4. Where the rule lives

- **`skills/flow-contracts/pipeline.md`, the transition table** — canonical for command → state
  transitions — gains one row: no command, a plain message, at `IN_PROGRESS` in a session whose
  last `/flow` run marked the change → fix run, state unchanged; and **Every invocation is
  re-entrant** gains the matching bullet. The bare-invocation rule that starts integrate is
  untouched: a plain message never integrates, only ever fixes.
- **`skills/flow/SKILL.md`** gains a subsection **A plain message at `IN_PROGRESS`** under
  **Reading the state**, carrying sections 2 and 3's rule: the trigger, the hook line or the
  session's own context as the source of `<name>`, the `flow state get` gate, the ambiguity
  prompt, the announcement ("Using flow for change `<name>` — fix run from a plain message"), a
  fresh `mf-` token, and the continuation into **3. Documenting a fix, before implementing it**
  with the verbatim message as the fix instructions.
- **`commands/flow.md` and `commands-claude/flow.md`** each gain one sentence beside "the
  argument is fix instructions", since both command trees must state the states the table row
  lists.
- **Budgets.** `skills/flow/SKILL.md` sits exactly at its `check-contract-budget.sh` row today
  (17812 bytes), so its row is raised to the new size plus 25%; the other touched files have
  room.

## 5. Installer, documentation and tests

- **Linking needs no change** — `install_hooks` and `install_hooks_zcode` link every file under
  `hooks/`. **Registration reporting does**: each function greps the config for the hook's name
  and prints a snippet when absent; both gain the same check for `flow-active-change` and a
  `UserPromptSubmit` snippet in the harness's own shape. `README.md` gains the hook's line in the
  tree listing and the `UserPromptSubmit` event in the ZCode step-2 snippet.
- **Tests.** `scripts/test-flow-active-change-hook.sh` is the hook's own harness (fixture
  transcripts under `mktemp`, stdin JSON piped to `python3 hooks/flow-active-change.py`), picked
  up by `scripts/run-guard-tests.sh`'s glob with no registration; `scripts/test-setup.sh`'s
  fixture repository gains a fixture `hooks/flow-active-change.py` and three assertions (the
  Claude link, the printed snippet, the ZCode link).
- **Live verification.** The hook is run against a real Claude Code transcript from this
  repository's project directory that contains a `/flow` mark, with a plain-prompt payload:
  success is the context line naming that transcript's change; failure is empty output, which is
  what the hook also prints for a transcript with no mark — so the check first confirms the
  transcript holds a `-command '/flow'` mark. The store-side effect is confirmed on the
  operator's first real unprefixed fix after registration: the change's run list gains a second
  `flow` run and `FixIterations` rises by one.

## Step-by-step breakdown

### The prompt hook

**What:** `hooks/flow-active-change.py`, a `UserPromptSubmit` hook that finds the last
`flow stage begin -command '/flow' … -session-token mf-… <name>` in the session's transcript and
injects one context line naming `<name>`; silent on a slash command, an unmarked transcript or any
fault.
**Why:** The change name has to be known deterministically on every plain prompt, after
compaction and hours into a session; the transcript holds every mark the run made and nothing
else does without a store round-trip.
**Uses:** the hook's stdin JSON (`prompt`, `transcript_path`, `session_id`), `CLAUDE_SESSION_ID`,
`FLOW_ZCODE_ROLLOUTS_DIR`, `~/.zcode/cli/rollout/model-io-sess_<id>.jsonl`, Python 3 standard
library only.

### The router rule

**What:** **A plain message at `IN_PROGRESS`** in `skills/flow/SKILL.md`, one transition-table
row and one re-entrancy bullet in `skills/flow-contracts/pipeline.md`, one sentence in each
command stub.
**Why:** The fix path exists; a plain message never reached it because the router is entered only
by an invocation. The rule states when a message is one, and hands it to the existing section 3
with a fresh token so the store sees an ordinary fix run.
**Uses:** `flow state get`, **3. Documenting a fix, before implementing it**
(`skills/flow/implement.md`), **The shape** (`skills/flow-contracts/operator-prompts.md`),
`scripts/check-contract-budget.sh`.

### Installer registration and documentation

**What:** `setup.sh`'s two hook installers report the new hook's registration and print its
`UserPromptSubmit` snippet; `README.md` lists the hook and carries the ZCode snippet.
**Why:** The installer links every hook already; what it must not do is claim a hook is
registered when it is not, and the paste is the operator's — the same contract the baseline hook
set.
**Uses:** `setup.sh` (`install_hooks`, `install_hooks_zcode`), `README.md`.

### The harnesses

**What:** `scripts/test-flow-active-change-hook.sh` with six cases, and three assertions plus a
fixture hook in `scripts/test-setup.sh`.
**Why:** A fail-open hook that prints nothing on error is indistinguishable from one that found
nothing; the harness pins each silent case to its cause and the one loud case to its exact line.
**Uses:** `scripts/run-guard-tests.sh`, `python3`, `mktemp`.
