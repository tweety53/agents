## 1. Problems encountered, and what pipeline change would avoid them

**The review panel took 9 rounds to converge on one defect class.** A symlink/path-traversal
trust-boundary bug in the new `gather-self-review-context.sh` script kept reopening in narrower
forms — leaf symlink → trailing slash → ancestor symlink → `..` traversal → extra nesting depth →
worktree-root confusion → unquoted glob — because each fix round closed only the specific bypass
shape the round's reviewer found, rather than stepping back to ask what the general invariant was.
Round 5 eventually replaced the whole bounded-hop approach with one general mechanism
(`validate_archived_path()`: lexically normalize vs. semantically resolve, then compare), which is
what finally stopped the reopenings. A pipeline change that prompted the fix-dispatch to ask "is
this bug a member of a class, or a one-off?" before writing a bounded patch — especially for
path/trust-boundary logic — would likely have reached the general fix by round 2 or 3 instead of
round 5.

**The review-panel record's own bookkeeping format tripped `check-unfinished-work.sh`.** That guard
requires the panel record to carry exactly one `findings-total:` line and one unbroken block of
`finding-status:` markers for the whole file — a fact stated in the guard's own header, which I
didn't consult before authoring nine rounds of `## Fix round N` sections, each with its own
`findings-total:`/marker block. `/myflow-finish` run 1's unfinished-work gate caught this
immediately and correctly, but only after the fact. A short note in `myflow-do`'s panel-record
guidance — "only the final round's marker block is live; every earlier round's findings go in prose,
never as `finding-status:` lines" — would have prevented this from ever needing a fix at the gate.

**The SDD ledger was never written.** `/myflow-do`'s "Execute (SDD + TDD)" section calls for a
literal ledger line per dispatch (`Task N: complete (uncommitted, review clean, model: <model>)`)
at `.superpowers/sdd/tasks/progress.md`. I tracked progress via the harness's task-list mechanism
instead, which is a live view, not a durable record — so `preserve-session-records.sh` reported the
ledger source as `skipped: ... (absent)` at finish run 1, and this self-review's own context bundle
is missing it too. The task list and the ledger serve different purposes and one is not a substitute
for the other.

## 2. Token/time cost, and what would reduce it without quality loss

**The "escalate to a full 7-slot re-run whenever a fix touches a delta spec" rule fired on nearly
every round**, because almost every fix to the trust-boundary logic required describing the new
refusal scenario in the delta spec — creating a fix → spec touched → full re-run → new finding → fix
→ spec touched again loop. By round 8, when the only remaining findings were pure documentation
drift with zero code change, I judged a full 7-slot round wasteful and ran a targeted 3-reviewer
confirmation instead (the three who'd raised the findings) — which caught the one leftover instance
that mattered, at roughly 3/7 the cost. Formalizing that judgment call — a fix whose spec change is
purely additive (a new scenario, no altered `SHALL`) and touches no code file may re-verify with a
targeted round scoped to the raising reviewers, reserving the full 7-slot re-run for fixes that alter
existing requirement text or any code file — would have saved a full round's cost on at least round
9, with no loss of coverage: the reviewers who would have caught a regression are exactly the ones
still included.

**Manual reproduction in my own shell, on top of the reviewer's own reported reproduction and the
growing test suite, was sometimes redundant.** By round 6–7 the test suite already asserted every
symlink/traversal shape a reviewer reported; re-running the exact exploit by hand myself, in
addition to reading the reviewer's own transcript and the test suite's pass, added confidence but
also token cost that a policy of "trust the test suite once it demonstrably covers the reported
shape, spot-check only when the suite doesn't yet cover it" would have avoided without losing safety.

## 3. What went well, and how to reproduce it

**Escalating panel breadth (never model) on repeated rounds, combined with instructing security-
relevant reviewers to physically reproduce an attack rather than reason about it abstractly, is what
actually found the real bugs.** F13 (trailing slash), F20 (`..` traversal), F22 (depth-assumption
fragility) and F23 (worktree-root confusion) were each found by a reviewer who built a real sandboxed
symlink/repo and ran the script against it, not by static reading. Every fix-verification round also
re-ran the *original* exploit from earlier rounds, not just the new one — which is what caught that
some fixes were narrower than they looked. **To reproduce:** for any change touching trust boundaries
or path validation, keep the full panel roster across rounds until a reviewer explicitly signs off
with a real, constructed reproduction (not code reading alone), and keep escalating breadth
automatically on each new finding rather than narrowing early.

**The "one combined fix subagent per round, with a full report of what changed and how it was
verified" pattern worked well.** Every fix report included the diff shape, the new test case, and a
manual reproduction proving the specific finding closed — which let the next round's reviewers (and
me) verify quickly without re-deriving the fix from scratch.

## 4. What could be automated or moved to a script

- **A panel-round bookkeeping helper** (`scripts/panel-round-append.sh <panel.md>`) that mechanically
  appends a new round's findings and folds the previous round's marker block into inert prose, would
  remove the entire class of formatting mistake found in angle 1 — the multi-round accumulation shape
  is repetitive enough to script rather than re-author by hand each round.
- **A fix-round diff-summary check** (line count, whether any delta spec changed, whether any code
  file changed) to *mechanically* decide targeted-vs-full escalation, rather than a judgment call
  made ad hoc each round — this is exactly the decision angle 2 flags as inconsistently applied.
