More brainstorming rounds, if needed

Brainstorming can already refuse to assume. What it cannot do is go back and ask again — so a question raised by an answer has nowhere to land. This change gives the stage a loop, a way to stop, and a record of what was left open.

Why

The gap is not that questions get assumed away. It is that there is nowhere to ask them.

skills/myflow-start/SKILL.md invokes superpowers:brainstorming "in full: checklist items 1–8", and that upstream skill's flow is linear — explore, ask, propose, present, approve. Its only loop is design revision, which routes a correction back to the design. Nothing routes a question back to the questions.

myflow-planning-gate already requires that an unresolved question be put to the operator rather than assumed. That covers a question the command notices. It says nothing about a question a previous answer created, because the stage has no way to reach a second round.

Two further asks arrived during this change's own planning run, both raised at gates this change is about — which is itself the argument for the loop.

  • TO DO URGENT should be read as To Do. KAN-36 sat at that status, the unrecognised-status carve-out fired, and the answer was that the status simply means To Do.
  • /myflow-start's git boundary contradicts itself three ways. Seven archived changes committed a design doc from it, so the normative requirement forbidding that has been violated by every change this pipeline has planned.
What

Four slices, three subjects

A and B are the issue's ask, split because the loop and the record are separable — the loop produces more rounds, the record is what makes stopping early honest.

A

One convergence test, applied after every exchange

After a question round, a design-section approval, or the spec review, the command asks itself one thing: does it now hold a question its inputs do not answer? While the answer is yes, another round opens. One test rather than a rule per gate means a gate added later inherits the loop instead of escaping it by not being enumerated.

A

Two prompts bound the loop, and they recommend opposite things

Each is reachable only under the fact that makes its own recommendation true. That is stated in the spec so a later editor does not harmonise them.

The confirm

fires when the test comes back empty

recommends → move on

The command states what it believes settled and asks whether anything is still unclear. Recommending move on is honest because the prompt is unreachable while the command holds anything at all.

The soft-bound offer

fires from the third round onward

recommends → another round

In place of silently opening a round, it shows what is still open and what it would ask. Recommending another round is honest for the mirror reason — the same shape as finish run 1's unfinished-work gate, where Stop is recommended.

The threshold is a tuned value living in skills/myflow-start/SKILL.md; the requirement says only that later rounds are offered rather than taken. There is no hard cap — no round count ends the stage on the command's own authority. Every planning effort level runs the loop: a level changes how many questions are grouped into a round, never whether another opens.

Decisions

Ten decisions, each with what ruled the alternative out

Sourced from the brainstorming dialogue. Every one was put to the operator as named options with a marked recommendation.

How brainstorming knows a round is the last one

convergence-test-plus-confirm active

Chosen
Both — the command loops while it holds unanswered questions, then confirms with the operator before moving on.
Considered
Agent-judged only — rejected because "everything should be clarified" would rest on the command's own judgment, which is the failure the issue reports. Operator-gated only — rejected because it costs a prompt per round even when nothing is open.

How far back the loop reaches

every-gate-routes-back active

Chosen
Every planning gate routes back — one convergence test after every exchange.
Considered
Questions stage only — rejected because a design section is where an unasked question most often surfaces, and routing it to a revision is what turns a question into an assumption.

Whether the number of rounds is bounded

soft-bound-from-third-round active

Chosen
A soft bound — early rounds open silently; from the third onward the round is offered as a named choice showing what is still open.
Considered
No bound — rejected because a command that keeps generating questions has no visible trajectory. Hard cap — rejected because it ships a known gap on a schedule rather than on a judgment.

Where a question that survives the last round goes

open-questions-section-in-design active

Chosen
An ## Open questions section in design.md, reaching the proposal artifact and the STARTED handoff count.
Considered
Also blocking its task in tasks.md — rejected because it couples two stages and stalls implementation on a deliberately deferred question. Nowhere — rejected because it makes the record transcript-only.

Whether a revision round re-enters the loop

revision-round-scoped-loop active

Chosen
Yes, scoped to what the feedback reopened and whatever that opens in turn.
Considered
Yes, in full — rejected because re-asking answered questions would make operators stop revising. No — rejected because a revision is exactly where a half-clarified plan surfaces.

How TO DO URGENT is taught to the pipeline

todo-urgent-enumerated-synonym active

Chosen
Enumerate it as a To Do synonym — an enumerated name at To Do's position, in the contract and the spec.
Considered
A configurable synonym map in .myflow/project.md — rejected as speculative generality: another untrusted-input path into a transition decision, and nothing today needs a second entry.

Whether a guard holds the two status enumerations in sync

synonym-set-cited-not-guarded active

Chosen
No guard — state the set once and have the join search cite it, which check-references.sh already checks.
Considered
A sync check — rejected because a script, a harness and a registry entry is more machinery than a two-name list warrants, and a citation removes the divergence rather than detecting it.

Where the rule is expressed across the layers

extend-existing-capabilities active

Chosen
Extend the existing capabilities; structure in pipeline.md, tuned mechanics in myflow-start/SKILL.md, one synonym set in jira-integration.md.
Considered
A new capability — rejected because planning-gate already owns "a question is asked, never assumed", and convergence is that requirement read forward. Skill-level only — rejected because the repo is spec-first by construction.

How wide the /myflow-start commit exception is

start-commits-all-planning-artifacts active

Chosen
All planning artifacts it writes — the design document and openspec/changes/<name>/ — in two commits at the points the run reaches them.
Considered
The design doc alone — rejected because it leaves the plan reaching the worktree by a route no document states. Any commit bounded only by "no implementation" — rejected because it gives up the path list that makes the boundary checkable.

Which way the commit contradiction is resolved

legalise-rather-than-forbid active

Chosen
Make the practice legal and bounded — modify myflow-command-surface to name /myflow-start for the planning paths.
Considered
Stop committing — rejected because a worktree created from the base branch would then never contain the plan its implementers read, and because it changes behaviour seven past changes relied on in order to fix a document rather than a defect.

Risks

What this change cannot guarantee

  • The convergence test is agent behaviour and no guard can check it. The requirement's scenarios and the operator at the confirm prompt are the whole enforcement — the same protection the planning gate's existing never-assume requirement relies on. The soft bound exists precisely to put the trajectory in front of the operator rather than trusting it.
  • The threshold is a judgment, not a measurement. It comes from the shape of a converging conversation. It lives in the tuned-values file so it can move without touching the requirement.
  • ## Open questions is a second immutable-ID section, and IDs reworded rather than reassigned are a failure mode ## Decisions already has. The rule is stated identically in both places, and the answered by link makes a stale ID visible.
  • Slice D legalises a commit on the base branch. That is existing behaviour and the slice does not widen it, but it is now written down and therefore reviewable. The bound that keeps it safe is the path list: two paths, planning-only, with no push, so nothing leaves the machine until /myflow-finish.
