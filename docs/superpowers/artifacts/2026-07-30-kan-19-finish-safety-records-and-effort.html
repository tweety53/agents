Finish safety, session records, and planning effort

/myflow-finish can decide a branch is merged when it was never committed, and then archive the change and force-delete the worktree holding all of it. This closes that, preserves two records that currently die with the worktree, accounts for a file nothing owned, and lets you size a change's planning once.

Why

/myflow-finish chooses between its integrating run and its archiving run with git merge-base --is-ancestor HEAD origin/$BASE. A branch whose work is staged but never committed still has HEAD at the merge base — so it is trivially an ancestor of the base branch, and the check answers merged.

This was reproduced on KAN-14. HEAD and the merge base were both the same commit, zero commits ahead of origin/main, with 29 staged entries totalling 8,543 insertions. Run 2 would have synced the specs, archived the change, pushed the archive, and run git worktree remove --force over all of it. Only a manual check stopped it.

The existing guard did its job: base resolution is protected against HEAD@{upstream}, and it correctly resolved main. The hole is elsewhere and unguarded — a branch with no commits of its own is an ancestor of every branch.

Two smaller gaps of the same family live in the same command. The SDD ledger recording which model ran each dispatch is gitignored and dies with the worktree, so myflow-model-policy currently has to disclaim its own record. And nothing removes the proposal artifact source /myflow-start writes beside the state file, so whether a finished change leaves one behind has depended on whether someone noticed.

A fifth item was added during this planning run: /myflow-start should ask what effort to spend on a change the first time it runs for it.

The decision, made executable

scripts/check-finish-preflight.sh takes a worktree, a resolved base ref and the merge base recorded in the state file, and prints exactly one verdict:

RUN1

Integrate. The branch has not reached the base branch — or has no commits of its own.

RUN2

Archive. Merged, distinct from the recorded merge base, and nothing outstanding.

REFUSE

Stop and ask, before anything is archived, synced, pushed or removed.

Three signals decide it, and the order is the fix:

  1. HEAD against the merge base recorded in worktrees. Equal means the branch has no commits of its own → RUN1, whatever the ancestor test says.
  2. The ancestor test — git merge-base --is-ancestor, or a PR CLI when one is usable.
  3. The worktree's cleanliness. Merged by ancestry with uncommitted entries → REFUSE.

Signal 1 precedes signal 2 because a zero-commit branch is an ancestor of everything — so signal 2 alone is wrong on precisely the most dangerous input. Signal 3 follows signal 2 because dirty-and-unmerged is the ordinary IN_PROGRESS state and must stay RUN1, not become a prompt on every finish.

The commit count is not a signal. The issue's first proposed fix — git rev-list --count $BASE..HEAD > 0 — is disproved in the ticket itself: a genuinely merged branch is also zero ahead once its commit joins the base branch. It would trade a rare destructive failure for a permanent one that blocks every finish.

Base-branch resolution stays in the contract and is passed in. The hard-won HEAD@{upstream} guard already lives there, and a second copy of a procedure gating a destructive operation is a second copy that can drift. On a multi-repo change the script runs once per worktree, and run 2 proceeds only if every one returns RUN2.

Run 2's existing cleanup checks would already have caught KAN-14's staged entries — they just run at step 4, after the irreversible archive-and-push at step 3. Signal 3 is those checks hoisted to a precondition.

Preserving what dies with the worktree

scripts/preserve-session-records.sh copies three files out of the gitignored worktree and into the repository. It runs at /myflow-finish run 1, before staging, so the records land in the same commit as the work they describe — and again on /myflow-do's commit path, so a fix round raised after a PR is open refreshes them.

SourceDestination
.superpowers/sdd/tasks/progress.md docs/superpowers/ledgers/<date>-<name>.md
.superpowers/sdd/final-review-panel.md docs/superpowers/reviews/<date>-<name>-panel.md
<state-dir>/<name>-proposal-artifact.html docs/superpowers/artifacts/<date>-<name>.html

Both destination shapes match what was kept by hand on KAN-8 and KAN-14. The date is fixed at the first copy — an existing file for the change is reused, so a fix round overwrites in place rather than leaving one dated duplicate per round. A missing source is reported and skipped, never fatal: a change may legitimately have no panel record, and a preservation step able to block an integration would be worse than the gap it closes.

The rest of .superpowers/sdd/ is let go, as it was by hand — the per-task diffs duplicate commits already in git history.

Durability must not soften unknown (agent-defined). Panel slots dispatched by agent type resolve their model from a definition the dispatcher never reads. KAN-14's own record listed two such slots as sonnet — a value nothing measured. A record that persists is a stronger reason to leave an unobserved entry unobserved, not a weaker one.

Run 2 then removes the state-directory artifact source, disclosed like the worktree removal — but only when the preserved copy exists. The terminal state file advertises artifactUrl forever; deleting the only source that could republish it would leave a URL advertised and unrepublishable.

The effort ask

/myflow-start asks once, on the run that creates the change — determined by the state file's absence, not by a guess about you or the conversation. A revision round reads the recorded level, says which it is reusing, and does not ask again. It uses the same interactive mechanism as /myflow-finish's integration question, so the no-flags rule is untouched.

LevelWhat it changes
lowQuestions batched rather than asked one at a time; the design presented once; tasks.md grouped more coarsely
mediumThe default. The checklist followed with related questions grouped
highEach checklist item worked separately, alternatives enumerated per open question, each design section approved on its own

No level may switch a gate off. Brainstorming runs, the design approval gate holds, writing-plans runs, and tasks.md is never left a scaffold — at every level. A lower level means fewer rounds, never fewer gates. The review panel's breadth is decided by its own escalation triggers and is never scaled from this field.

The storage is the interesting part. state-self-heal.md closes the state-file schema in both directions — a file missing a documented field is unparseable, and a file carrying an undocumented key is unparseable too. Adding effort naively breaks both ways at once.

So it is documented as a field whose absence is a legal value, meaning "not recorded" — different from the present-and-nullable shape artifactUrl, jiraIssue and prUrl have. Requiring the key would route all three existing finished changes through self-heal, which announces unrecovered fields and rewrites from artifact inference: a loud correction for a value nobody had the chance to set.

Decisions

Split KAN-19, shipping the finish items first

split-finish-first active
Chosen
Items 2, 3 and 4 here; item 1 (the provenance guard's scan scope) separately — they share no file, and item 3 destroys work, so it must not wait behind a parser rewrite.
Considered
One change covering all four — one review panel and one merge, but a plan mixing a Python parser rewrite with a git-safety contract change, holding the destructive bug behind it. Item 3 alone as a hotfix — fastest, but leaves three follow-ups open and re-opens /myflow-finish three times.

A missing recorded merge base refuses and asks

missing-merge-base-refuses active
Chosen
Stop, report HEAD, the base and the uncommitted count, and require explicit confirmation — no recorded merge base is an honest unknown, and this change exists because a check returned a confident wrong answer where an unknown was available.
Considered
Fall back to the ancestor test plus a clean-tree check — catches the KAN-14 shape without input, but a committed-then-reset worktree passes silently. Refuse with no override — safest, but locks out every pre-fix state file and invites hand-editing it.

Run 1 preserves the session records, not run 2

preserve-at-run-1 active
Chosen
Run 1, before git add -A — the records land in the same commit as the work and merge with it, they survive a change merged but never archived, and run 2 gains no new write before its irreversible steps.
Considered
Run 2 before worktree removal, as the issue suggested — but it adds a write to the one command performing irreversible operations, and loses the record for a change that merges without being archived. /myflow-do authoring them in-repo from the start — maximum durability, but it puts per-task ledger churn into the diff you review.

Preserve the ledger and the review panel record, and nothing else

preserve-ledger-and-panel active
Chosen
Exactly what was kept by hand on both prior changes — the ledger answers "which model ran this task", the panel answers "what was found and how it was resolved", and nothing else reproduces either.
Considered
The ledger alone — smallest, and all myflow-model-policy strictly needs, but it drops a record you chose to keep by hand twice. Everything under .superpowers/sdd/ — nothing to decide per change, but per-task diffs duplicate commits already in git history.

The artifact source is preserved in-repo, then removed from the state directory

artifact-source-preserve-then-remove active
Chosen
Copy it into the repository at run 1 with the other records; remove the state-directory copy in run 2's disclosed cleanup — the recorded URL stays republishable from git history, and the state directory stops growing by one file per finished change.
Considered
Delete at run 2 with no preservation, as KAN-8 and KAN-10 did by hand — simplest, but the terminal state file advertises a URL whose only source is gone. Retain it in place and say so — zero machinery, but unbounded growth and it still looks like litter.

The run-2 decision becomes an executable script with a test harness

preflight-as-script active
Chosen
check-finish-preflight.sh plus its harness, matching this repository's three existing check/test pairs — the one item with real branching logic becomes the one item a test can hold to account.
Considered
Prose contract only — consistent with every other finish rule and nothing to install, but the fix would be verified only by review, exactly as the broken version was. A script for the decision with prose for the rest — smallest executable surface, but it leaves the copy step, with three sources that can each be absent, untestable.

Effort governs this /myflow-start run's reasoning, and nothing further

effort-scopes-this-run active
Chosen
The answer sets how much reasoning /myflow-start spends on its own brainstorming and plan enrichment; later commands decide their own depth.
Considered
Pipeline depth across all three commands — one question sizes the whole change, but a value chosen before anything was known could silently thin the panel that catches implementation defects, the one place this pipeline deliberately does not economise. Both as one scale — simplest to answer, but it conflates a planning budget with a review one.

The chosen effort is recorded in the state file

effort-in-state-file active
Chosen
A new effort field, written by /myflow-start and carried forward verbatim by every other command — the shape jiraIssue already has, so the carry-forward duty needs no new mechanism.
Considered
Recording it in the proposal artifact only — human-readable with no schema change, but a command would have to parse markdown to read it, which nothing in the pipeline does. Asking fresh each run — no schema change, but you answer repeatedly and a revision round could silently contradict the first.

What this deliberately leaves alone

  • Item 1 of KAN-19 — widening the provenance guard's scan scope past tasks.md. A separate change under the same ticket.
  • Commit messages, which the issue notes are outside any guard's reach.
  • A verification gate in /myflow-finish. The preflight checks the branch's own state; it runs no tests and no linters. That rule stands.
  • Effort governing /myflow-do or /myflow-finish. Widening it is a change to those commands' specs, not a reinterpretation of this field.
