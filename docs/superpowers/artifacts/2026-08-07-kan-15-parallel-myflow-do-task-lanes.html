A database per workspace

One change's migrations land under another change's tests, and the failure looks like a real test result.

planning effort · default implementer · Opus panel · Sonnet panel fixes · Opus 2 repositories not breaking 11 tasks docker-compose.yml untouched
Fourth revision — three designs were rejected before this one

In-run lanes split one plan into concurrent task groups joined by patch. Lanes as branches gave each its own PR — until a lane with its own branch, worktree, panel, gate and finish run turned out to be a change. The dev stack in containers reached four dev Dockerfiles, a compose profile, bind mounts and two run modes. Each is preserved in design.md as superseded decisions rather than deleted.

This one is what remains once the actual problem is named: not the stack, the database. The change name still says "lanes" and is kept deliberately — this artifact's source path derives from it, and a revision must republish to the same URL.

Why

Two apply worktrees share one Postgres database. One change's Flyway migrations alter the schema the other is testing against — "when db schema is different between them it can produce false positive testing results", as KAN-15 puts it.

Two adjacent resources fail the same way once changes genuinely run at once: Redis holds sessions and cache in one index, and MinIO has a single bucket. And the apps bind fixed ports, so a second devStart cannot start at all — which is what makes concurrency impossible today whatever the database is called.

What is namespaced, and what is left alone

The data services stay shared containers on their current ports. What gets a per-workspace name is the logical resource inside each one.

docker-compose.yml is not edited at all. Every earlier revision of this design parameterized it; none needed to. Duplicating whole services per workspace solves a problem that lives one level down, inside one of them.

The cache index is the one value that is probed, not derived

Everything else comes from the workspace id's digest. Redis cannot: it offers 16 indices, so a digest modulo 16 collides at roughly 6% for two concurrent workspaces — silently sharing sessions and cache, which is the exact failure class this change removes. devStart claims the lowest free index instead and records it for the run. The cost is that the index is not stable across restarts, which does not matter for sessions and cache.

Isolation is automatic, not opt-in

A worktree is isolated without being asked; the main checkout always gets the defaults. Nothing is behind a flag, because forgetting a flag would silently reproduce the original bug. An operator who deliberately wants the shared database passes the -PpgDb that already exists.

The five facts this rests on

  • application.yml already has ${DB_URL:jdbc:postgresql://localhost:5432/gymie} — but application-local.yml hardcodes the same URL with no placeholder, and local is the profile development runs. That one line is the pivot of the whole gymie change.
  • dbReset already takes -PpgDb, already runs DROP DATABASE IF EXISTS … WITH (FORCE) then CREATE DATABASE "$pgDb", correctly quoted. The per-database machinery exists; it is only ever pointed at one name.
  • The gateway has no datasource — only the backend touches Postgres, which halves the surface.
  • dbSeed starts :app:bootRun --spring.profiles.active=local, so it inherits exactly that hardcoded URL.
  • The integration tests use Testcontainers, so the test database is already ephemeral. The suite is untouched.

Delta spec

One new capability. No existing capability's requirements change.

myflow-workspace-isolation
  • A workspace id is derived from the change name
  • An apply worktree is isolated automatically
  • The id derives the database, object store and ports
  • The cache index is claimed by probing, not derived
  • A workspace's database and bucket are created on demand and start empty
  • Database maintenance tasks target the workspace's own database
  • Application URLs follow the workspace's ports
  • The test suite is unchanged
  • A workspace's database and bucket are removed at finish, and a missing service is skipped
  • Projects declare their isolation through an optional configuration section
