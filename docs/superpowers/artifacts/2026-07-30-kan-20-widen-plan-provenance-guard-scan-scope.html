KAN-20 · Proposal · agents

Widen the plan-provenance guard's scan scope beyond tasks.md

The guard reads a change's tasks.md and nothing else. Its design.md and proposal.md make numeric claims like any plan, and nothing checks them. This widens the scan — and first removes the two false-positive classes that widening would expose.

What the measurements changed

The ticket predicted the numeric rule would "fire heavily", projecting up to seventy-odd hits per design.md from a bare-number proxy. The guard's real classifier only fires on a digit group followed by one of eight unit words, so the true cost is an order of magnitude smaller. Every figure below comes from calling the guard's own ProvenanceGuard.check_file directly.

Zero classification aborts means the container-prefix grammar already handles these file types. Of the hits, most are false positives in two classes — a self-referential quotation of the historical invented baseline, which the provenance documentation must reproduce to explain itself, and an issue key read as a quantity, where KAN-6 errors parses as a count of errors.

The premise, corrected

Scope was not the binding constraint. Of the four defects the ticket cites as motivation, widening the scan would have caught essentially none. The most-instanced one — measured: tags citing a ref where the cited scripts do not exist — had most of its instances inside tasks.md, already fully in scope, and the guard passed clean on them.

The guard checks that provenance is stated, never that it is true. That boundary, not the file list, is what let those defects through. Verifying the @ <ref> half of a tag is deliberately left to its own ticket rather than smuggled in here.

What this change genuinely buys: two unattributed numeric claims the guard cannot currently see, a false-positive class removed before it can provoke a suppression marker, and a module docstring corrected to describe the behaviour the code actually has.

Decisions

scope-not-truth

Widen the scope and fix its false-positive classes, rather than re-aiming at tag truth

Stay close to the ticket, and be honest that this catches two real defects rather than the four cited.

Considered: block rule only — zero cost, but close to a no-op on this repository's evidence. Re-aiming at ref verification — what would have caught the most-instanced defect, but it amends a deliberate documented boundary. Both together — wants decomposing into two changes.

specs-excluded

A change's specs/ directory stays out of scope

Spec text legislates rather than describes, and a requirement forbidding a shape must be able to name that shape.

Considered: including it — immediately raises why openspec/specs/, the synced copy of the same text, stays unscanned. Including it for the block rule only — invents a per-file rule split to save nothing measurable.

quotation-syntactic

The quoted-number false positive is fixed syntactically, not with a fifth tag

A number enclosed in matched double quotes or an inline code span is a quotation, not a claim. Line-scoped, and fails closed — an unmatched delimiter exempts nothing.

Considered: a fifth tag quoted: — auditable, but it amends "four tags exist, and no others" to cover instances that are all the same self-referential quotation. A hybrid — more surface to specify and test for a case that has not arisen.

The plan

Ordered so the repository never passes through a state where the widened scan reports a false hit on its own tree: classifier fixes first, scope second, contract last.

  1. Stop reading an issue key as a quantity

    A fixed-width lookbehind on the numeric pattern, plus the docstring sentence that described a property the code lacked.

  2. A quoted number is reproduced, not claimed

    A line-scoped, fail-closed enclosure predicate, routed through the single existing claim-check method.

  3. Scan design.md and proposal.md

    The scan set, a generalised containment gate covering every scanned file, and the restated scan-integrity invariant.

  4. Bring the contract into line

    The scope section rewritten, the exemption documented, and what did not change said plainly.

Out of scope

  • Tag truth. Verifying that a measured: tag's ref resolves, or that its cited command exists there. It deserves its own ticket.
  • Commit messages. Outside any guard's reach, as the ticket itself records.
  • The published openspec/specs/ tree. Excluding a change's specs/ keeps this consistent by construction.
Once this ships, the guard scans this change's own design.md and proposal.md, and /myflow-do runs the lint step at the end of its run. Those artifacts are written tag-clean under the new rules from the start — the most direct end-to-end proof that the widening works.
