myflow proposal · kan-111-myflow-fast

One command from idea to merged branch, minus the parts only a human can do

state: STARTED KAN-111 · In Progress effort: default

01Why

The myflow pipeline already removes most of the ceremony around shipping a change, but three separate commands still stand between an idea and a merged branch, and two of the seams between them carry no human decision at all. /myflow-fast collapses those seams into one command, so the only manual work left is what only a person can do: answering brainstorming's design questions, reading the diff, running the app, and choosing how the branch lands.

02What one invocation does

The first call runs brainstorming exactly as /myflow-start does today — full interactive dialogue, nothing auto-answered — then continues, in the same run, straight into implementation and the review panel. No command is typed in between.

Interactive Brainstorm design questions, one at a time
──▸
Unattended Implement + review SDD·TDD, light panel
──▸
You Review diff · run app the one gate that stays
──▸
You choose PR · merge+push · manual bare re-invocation
──▸
Auto where possible FINISHED archived, cleaned up

Re-invoking with text at IN_PROGRESS is read as fix instructions instead of a route choice — see below.

03What happens at the landing question

Once you review the diff and call /myflow-fast bare, it asks how to land the branch. What happens next depends on the route:

merge + push

Nothing external blocks it, so the same invocation merges, pushes, archives, and cleans up — ends at FINISHED with no further command.

open PR

Needs a human merge on the forge. Opens the PR, prints the URL, stops. A bare call after merge runs the archive.

manual

You integrate yourself. Hands off exactly as /myflow-finish does today; a bare call once merged runs the archive.

05Decisions

Chain start + do in one invocation chain-start-and-do-in-one-call
Chosen — no human gate sits between brainstorming converging and implementation starting today, so nothing is lost by not stopping there.
Considered — stopping at STARTED and requiring a second bare call — reintroduces exactly the friction this change removes, for a boundary nothing was ever gating.
Fix vs. integrate by argument presence arg-present-means-fix
Chosen — an argument at IN_PROGRESS means fix instructions; bare means proceed to the integrate question. No extra confirmation prompt.
Considered — always asking "fix or integrate?" explicitly — unambiguous, but a manual step on every re-invocation.
Merge+push auto-archives merge-push-auto-archives
Chosen — nothing external blocks it once chosen, so run 1 and run 2 happen in the same invocation.
Considered — stopping after merge+push like a normal run 1 — mirrors the existing contract, but gates a step nothing was actually gating.
PR route stops and hands off pr-route-stops
Chosen — a PR needs an external human merge, so nothing can auto-continue past it.
Considered — polling until merged — ties up a long-running session or needs a background job for an event this pipeline has no mechanism to observe.
Model defaults: Sonnet everywhere sonnet-everywhere
Chosen — implementation, review panel and panel fixes all default to Sonnet, trading the normal pipeline's Opus-for-implementer default for lower cost and latency.
Considered — keeping Opus/Sonnet/Opus — rejected since reaching for the fast path already signals a speed preference.
Panel roster defaults to light light-roster-default
Chosen — matches the project-wide default already set by KAN-110.
Considered — standard — broader coverage, slower fix cycles; kept for later if a specific change warrants it.
No proposal artifact no-proposal-artifact
Chosen — the operator who answers brainstorming's questions is present in the same session that produces the design, so a published summary of that same conversation adds no information.
Considered — publishing anyway for parity — pure overhead for a command whose purpose is cutting steps that carry no new information.
A driver, not a fourth state driver-not-new-state
Chosen — /myflow-fast reads and writes the exact same three-state machine and state-file shape as every other command — no new field, no new state.
Considered — a parallel lightweight state machine — rejected so every existing tool (/myflow-status, Jira integration, the finish contract) already understands a change this command touched.
