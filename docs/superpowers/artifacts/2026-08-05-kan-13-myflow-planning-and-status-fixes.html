1 Why

/myflow-start produced a plan for KAN-9's frontend whose task order left :shared uncompilable from Task 2 until Task 9 — seven consecutive tasks whose own "run the tests" step could not run at all, two tasks merged mid-flight to reach a compilable state, and a plan that needed human-adjudicated repair mid-run.

Separately, /myflow-status — and, via the same shared resolution logic, every other /myflow-* command — enumerates open changes from openspec list --json alone. That command only sees change directories present in the checkout it runs in, so a change whose planning artifacts exist only in a worktree is silently invisible, even while it sits at the human gate with a fully staged diff.

2 What changes

  • Every task /myflow-start produces now carries a required **Build:** tag — green, or red — merges with Task <N> — declaring whether the build (and that task's own verification command) is left runnable.
  • A new guard, run before the proposal artifact publishes, fails the plan when a task has no tag, a red tag names no partner, or a chain never resolves to green.
  • A new contract file, skills/myflow-contracts/build-green.md, becomes canonical for the tag vocabulary and the guard's scope — indexed alongside the other five contract files.
  • The one shared ## Change name resolution section every /myflow-* command reads is fixed to enumerate the union of openspec list --json and the project's state directory, not openspec list --json alone.
  • /myflow-status's own listing step is updated to cite that shared section instead of running its own independent enumeration.

3 Decisions

bundle-scope

Bundle both agents-repo items into one change

ChosenBoth KAN-13 items scoped to this repo, in one change — they surfaced in the same KAN-9 run and bundling avoids two proposals sharing one Jira issue with near-identical context.
ConsideredTwo separate changes mirroring KAN-9's repo split (rejected — these share a repo and neither depends on the other, so splitting by fix adds review overhead for no isolation benefit); scoping to the planning rule alone and deferring the status fix (rejected — the status fix is small and already fully specified).
build-green-mechanism

Build-green check is a structural tag, not a semantic build check

ChosenA required per-task **Build:** tag with a merge-partner rule, checked structurally — mirrors the existing verified:/unverified: provenance-tag pattern, generalizes to any reason a task is red, costs one line per task.
ConsideredA file-touch-graph heuristic (Creates:/Modifies:/Deletes: per task) — catches the literal KAN-9 shape but only that shape, and needs a new required field; a fully automated semantic/AST compileability check — infeasible in general and over-engineering for what the postmortem needed.
enumeration-fix-scope

Fix the shared resolution section, not just /myflow-status

ChosenFix pipeline.md's one shared section — KAN-13 itself flags that /myflow-finish's resolution has the identical blind spot and uses the same code path, so fixing it once fixes every command and prevents drift.
ConsideredFixing only /myflow-status/SKILL.md's step 1 — narrower and faster, but leaves /myflow-do and /myflow-finish silently exposed to the exact bug this change exists to close.

5 Specs

New capability — myflow-build-green

Requirement: Every task in a plan declares its build state

/myflow-start's writing-plans stage SHALL tag every task in tasks.md with **Build:** green or **Build:** red — merges with Task <N>, naming at least one partner for a red tag.

Scenario — a task's ordering could not leave the build green alone → tagged red — merges with Task <N>, naming its dispatch partner(s)
Scenario — an ordinary task leaves the build green → tagged green

Requirement: A guard enforces the build-state tags before the proposal publishes

A guard script SHALL fail the run when a task has no tag, a red tag names no partner, a named partner doesn't exist or isn't green, or a red chain never resolves. It SHALL NOT attempt to verify that a green tag is true.

Scenario — a missing tag blocks publish → guard fails, naming the task; the artifact is not published until fixed
Scenario — an unresolved red task blocks publish → guard fails, naming the unresolved task
Scenario — a resolved red chain passes → every red task names a partner that exists and is green
Scenario — the guard does not claim to verify truth → a falsely-tagged green task still passes; the guard checks presence and consistency, not truth
Modified capability — myflow-command-surface

Requirement: Change name resolution enumerates every state-tracked change

The shared resolution used by every /myflow-* command SHALL enumerate the union of openspec list --json and the project's state directory, minus anything archived. An unreadable state file SHALL be reported and skipped, never silently dropped.

Scenario — a worktree-only change is discovered → /myflow-status lists a change whose openspec directory exists only in a worktree
Scenario — every command shares the same enumeration → /myflow-do / /myflow-finish ask among the same match set /myflow-status would show
Scenario — an archived change is not re-surfaced → a state file whose openspec directory moved to archive/ is excluded
Scenario — an unreadable state file is reported, not silently dropped → skipped from the union and named in the report
