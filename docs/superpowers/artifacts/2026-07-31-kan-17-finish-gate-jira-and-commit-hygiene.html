Finish gate, Jira projection, and commit hygiene

Slice A of KAN-17: the twelve asks that change how the pipeline behaves. Three of the surfaces they touch have no normative source at all — and each has already produced a defect nothing caught.

Why

Jira. jira-integration.md is contract text with no capability behind it. It moves an issue to In Review “once a PR is confirmed open” — so a change that lands by merge-and-push never reaches In Review at all.

Evidence · KAN-20 changelog

To Do→ In Progress→ In Review→ Done

Two transitions recorded, not three. KAN-20 landed by merge-and-push, so the PR condition never fired. The same file orders statuses by name, which leaves TO DO URGENT — where KAN-13 and KAN-17 both sit — with no position in the order at all.

The integration gate. Nothing checks that a branch is finished before it is integrated. The kan-6 branch merged carrying an unfixed defect and unticked manual-test boxes. That is knowable today only because it was typed into a chat transcript.

The review panel’s bar. “Zero open Critical/Important findings” lives only in a guardrail line, with findings recorded as free prose — so a minor finding can be deferred with nothing able to notice.

Alongside these, the diff you review is filtered rather than clean: planning artifacts are staged and then hidden by a pathspec at display time, so they reappear in the IDE’s staged-changes pane and in git status.

What changes

  • Jira becomes normative. A capability holds the transition points, ordering, the unknown-status ask, labels, description sync, and the never-a-gate invariant.
  • In Progress fires when planning begins — immediately after the key resolves, before brainstorming. Failure still degrades to one skipped-with-reason line.
  • In Review fires at the end of finish run 1 on every route — PR, merge and push, or manual.
  • An unrecognised status is asked about, never inferred from statusCategory.
  • Created issues carry the parent’s labels plus AI-generated. No label is invented.
  • A run-1 gate refuses to integrate silently over unfinished work, offering continue, stop, or file a task — and recording the choice to continue in the planning commit’s message.
  • Findings become countable: a required table with a status per row, and no handoff while any row is open, at any severity.
  • Planning artifacts leave the staged diff, and finish commits them separately from the implementation.
  • Cleanup becomes one registry, and the remote branch — which nothing deletes today — is removed at run 2 and verified.
  • /myflow-start asks rather than assumes, and offers options wherever it asks for approval.

Decisions

Fifteen, each recording the alternatives that were on the table and the tradeoff that ruled each one out.

jira-in-progress-at-start In Progress fires when planning begins

ChosenTransition immediately after the key resolves, before the first brainstorming question — the board is then correct while a long planning run is in flight.

ConsideredKeep it after the state write and report the status more loudly — does not fix the board during the run. Treat the ask as subsumed by the unknown-status fix — you wanted the earlier timing on its own merits.

Trade-offAn abandoned planning session leaves the issue In Progress with no change to show for it. Non-blocking is preserved: a failure is still one line, and the state write later is untouched.

jira-in-review-any-route In Review fires on every landing route

ChosenAt the end of a successful run 1, whichever route was taken. Route-independence is the fix; conditioning on a PR is what broke it.

ConsideredKeep the PR condition and add the manual route — merge-and-push would still skip In Review. Fire at the start of run 1 — would claim In Review even when the push then fails.

jira-unknown-status-ask An unrecognised status is asked about

ChosenShow the key, the current status and the target, and ask whether to transition.

ConsideredOrder by statusCategory — the important rejection: TO DO URGENT and In Progress share indeterminate, so the issue reads as already at the target and the board freezes for the whole change. Declare the order per project — a second list that misorders silently when stale. Treat unknown as before In Progress — would drag a status like Blocked backwards.

jira-created-issue-labels Created issues inherit the parent’s labels

ChosenThe parent issue’s labels, plus AI-generated; no label is ever invented.

ConsideredAI-generated alone — follow-ups lose the routing label that makes them findable. A label list in project config — another list to maintain.

unfinished-work-script The run-1 gate is a script, not prose

Chosenscripts/check-unfinished-work.sh prints one verdict line, in the shape check-finish-preflight.sh established.

ConsideredProse contract only — prose is the enforcement class that already failed, in the kan-6 case this ask exists to prevent. Adding it to ## lint — would fire on every change in flight, which is the normal mid-work state.

unfinished-work-signals Four signals count as unfinished

ChosenUnticked guide boxes; unchecked plan items including nested fix sub-changes; findings not closed; and a ## Known incomplete section.

ConsideredThe guide’s boxes alone, which is the literal ask — you widened it to all four.

known-incomplete-location Undone work lives in the test guide

ChosenA ## Known incomplete section in docs/manual-test/<name>.md, refreshed on every fix run.

ConsideredThe panel record — an audit file you don’t normally open. A state-file field — that file carries only fields with a live consumer and records no human judgment. proposal.md — buried in an artifact read once.

Why it needs a homeFinish runs in a different session from /myflow-do and has no memory of it.

unfinished-work-prompt The gate offers three answers

ChosenContinue and integrate anyway; stop so you can finish it; or file a Jira task and continue.

ConsideredA fourth answer handing back to /myflow-do inline and resuming — you ruled it out as making one command re-enter another mid-run.

unfinished-work-audit Continuing past the gate is recorded

ChosenThe outstanding list appears in the handoff and in the planning commit’s message, so the git history answers whether anything was known to be unfinished at the merge.

ConsideredHandoff only — the record dies with the scrollback, which is how the kan-6 case became unprovable. A Jira comment too — a third write to keep consistent for no durability the commit message doesn’t already give.

findings-table-and-bar Findings become countable, and every severity blocks

ChosenA required table — slot, severity, location, status, note — whose status is open, fixed or withdrawn. No handoff with any row open.

ConsideredA checkbox per finding — severity and slot stay in prose, so nothing could report which slot raised what. No format, with the agent asserting the bar is met — an unverifiable claim is how minors got deferred before.

Where a dispute endsThe panel’s existing ladder hands back to you at the last fix round, and withdrawn is written there, by you, with a reason. That is the existing human gate — the one place a minor can end up unfixed.

findings-spec-home The findings bar joins the existing panel capability

Chosenmyflow-review-panel-economics — one capability for what the panel costs and what it must produce.

ConsideredA new findings capability — two specs about one panel makes “which do I amend?” a question. myflow-command-surface — about the command surface, not review quality.

planning-artifacts-unstaged Planning artifacts leave the staged diff

Chosen/myflow-do stages everything except openspec/, docs/manual-test/ and docs/superpowers/; finish commits implementation first and those paths second; a fix run with a PR open makes the same two commits.

Consideredopenspec/ only, the literal ask — the guide and preserved records would stay in the reviewed diff. Planning commit first — the newest commit on the branch would be a docs commit, which is the one a forge shows first. Splitting at finish only — the split would hold for the first integration and not for any fix pushed to the PR.

VerifiedThe exclusion pathspec was run in a scratch repository: it stages the code file alone and leaves both excluded paths untracked.

exclusion-list-fixed The exclusion list is fixed in the contract

ChosenThe three paths, named in the contract.

ConsideredA per-project key — the pipeline chooses these paths itself, so no project can currently differ, and an unset key would need the fixed list as its default anyway.

cleanup-registry Cleanup becomes one registry, and the remote branch joins it

ChosenOne table listing every artifact the pipeline creates, plus automatic deletion of origin/openspec/<name> at run 2, treating an already-absent branch as success.

ConsideredAsking before the remote delete — run 2 has already proved the branch is an ancestor of the base branch, so nothing can be lost. Gating it on the local delete succeeding — leaves the remote branch behind whenever anything unrelated failed.

cleanup-verification-script Run 2 verifies the registry with its own script

Chosenscripts/check-cleanup-complete.sh, returning a verdict the way the run-1 gate does.

ConsideredProse reusing the existing per-removal verification — this was the recommendation; you chose mechanical enforcement instead. Folding it into the run-1 guard — a different question at a different time, and no script here answers two.

planning-gate-always-ask /myflow-start asks rather than assumes

ChosenA myflow-planning-gate capability with two rules — every unresolved question goes to you, and every approval is offered as options.

ConsideredAdding it to myflow-effort — that spec’s subject is the effort level. Contract text with no spec — reproduces the unspecced shape this change fixes elsewhere. Scoping the options rule to one command — one rule covering every command subsumes both readings of ask 13 and costs a sentence.

The plan

Ten tasks, ordered so the two guards exist before anything references them and the canonical contracts land before the skills that point at them — no task leaves a dangling cross-reference for check-references.sh to catch.

  1. 01The run-1 gate script check-unfinished-work.sh and its harness — four signals, one verdict line, a missing file counts as outstanding
  2. 02The run-2 cleanup verification script check-cleanup-complete.sh and its harness; both harnesses join ## test, neither joins ## lint
  3. 03The Jira projection contract transition timings, the unrecognised-status rule, the labels rule
  4. 04/myflow-start — the earlier transition and the planning gate the call moves from section F to section A; two new guardrails
  5. 05The staging split the exclusion pathspec, the unfiltered review command, git boundaries
  6. 06The findings table and the every-severity bar column order is load-bearing — the guard counts the fourth cell
  7. 07## Known incomplete in the manual test guide the heading must be spelled identically in the skill and the guard
  8. 08Finish run 1 — the gate, two commits, In Review the gate precedes the landing question; implementation commits first
  9. 09Finish run 2 — registry, remote branch, verification every scattered removal rule becomes a pointer to one table
  10. 10README and the final sweep all three guards, all five existing harnesses, both new ones, and a sandboxed installer run

Risks and trade-offs

  • An abandoned planning run leaves its issue In Progress. Accepted — the board being correct during a long run was judged worth more, and you can move it back.
  • Every severity blocking can cost fix rounds on matters of taste. Bounded by the panel’s existing handback at the last fix round.
  • Guides predating this change have no ## Known incomplete section and will prompt once at their next finish. Correct, and self-clearing.
  • Two scripts and two harnesses is the heavier option. Chosen deliberately for mechanical enforcement over prose.
  • Unstaged planning artifacts sit untracked between /myflow-do and finish. Finish stages them before its second commit, and run 2’s existing untracked-file check would refuse to remove a worktree still holding them.
