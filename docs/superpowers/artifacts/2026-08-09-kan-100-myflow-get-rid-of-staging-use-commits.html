Get rid of staging — use commits

Per-task commits replace the uncommitted-diff review model in /myflow-do, and six new mechanically-checked task fields catch what self-reports used to miss.

state STARTED effort: default implementation: Sonnet review panel: Sonnet panel fix: Sonnet roster: light
Why What changes Design Decisions Open questions Capabilities Tasks

Why

/myflow-do implements every task uncommitted, reviews it via a checkpoint/diff snapshot, and leaves everything staged for the human gate. Nothing mechanically checks a task's claims — which files it touched, whether declared tests exist, what regresses on revert, the real baseline test count — against anything real. KAN-71 surfaced concrete cases where the self-report was wrong and nothing caught it before review:

  • "a task declaring 3 files touched 11"
  • "a task claiming 4 new tests wrote zero"
  • three defects shipped behind green suites
  • "a reported test count off by 600"

Real per-task commits give guards something to check against.

What changes

  • /myflow-do implementers commit each task (task(<n>): <subject> + Task-Id: trailer) right after finishing it, before review. NO-COMMITS is replaced by COMMIT-PER-TASK.
  • Review reads a real commit diff instead of a checkpoint snapshot. checkpoint and uncommitted-review-package are retired.
  • Fix-round changes commit as git commit --fixup=<task-sha> and are autosquashed into the task commit immediately, before re-review.
  • Six new per-task tags — Files:, Tests:, Regression:, Baseline:, Squash-with:, Commit: — written at plan time and checked by a new runtime guard against the real commit.
  • Squash-with: replaces Build: red's inline — merges with Task <N> text.BREAKING
  • /myflow-finish run 1 gains one step before its existing two-commit sequence: git reset --soft <merge-base>, collapsing every task/fixup commit. The branch still ends with exactly two commits.

Design

Goals

  • Give each task a real commit, so review and new guards check something real instead of a snapshot.
  • Add per-task fields a runtime guard checks against the actual commit, immediately after it's made.
  • Keep the final branch shape /myflow-finish produces unchanged — two commits, same as today.

Non-goals

  • Bisectable per-task history on the merged branch — per-task commits exist for review and checking during /myflow-do, not for the merged history.
  • Any change to the review panel's slot roster, model policy, or escalation ladder.
  • Any change to /myflow-finish run 2 (archive/cleanup).

Risks / trade-offs

RISKBaseline: runs the project's full test command twice per task MITIGATION accepted cost of the check the ticket asks for; skip-not-verified fallback already covers unsupported tooling.
RISKgit rebase --autosquash could conflict with a downstream fixup MITIGATION tasks dispatch serially, so a task's fixups always fold before the next task starts.
RISKretiring checkpoint scripts breaks any in-flight /myflow-do run MITIGATION no cross-version guarantee exists; finish under the old skill or re-plan.

Decisions

Squash everything at finish, not bisectable-per-task history

squash-everything-at-finishstatus: active
Chosenfinish collapses every task/fixup commit into one implementation commit — final history unchanged from today's shape.
Consideredbisectable per-task history, which the ticket's own rationale for Squash-with: suggests. Rejected — confirmed twice with the operator, who saw the tension and chose the single-commit shape regardless.

Fix rounds commit as git commit --fixup, autosquashed immediately

fixup-autosquashstatus: active
Chosenevery fix-round commit targets its task via --fixup and folds in immediately, so review always reads one commit per task.
Consideredleaving fix commits unfolded. Rejected — the ticket names --fixup as Task-Id:'s reason for existing, and unfolded fixups would spread the guard's checks across multiple commits per task.

A runtime guard, not a plan-time-only guard

runtime-mechanical-guardstatus: active
Chosenthe new field guard runs during /myflow-do, against the real commit, right after each task is committed.
Considereda plan-time-only check, like plan-provenance and build-green. Rejected — the point of these fields is catching a mismatch between claim and commit, which a plan-time check can't see.

Squash-with: replaces Build: red's inline partner text

squash-with-replaces-red-suffixstatus: active
ChosenBuild: red becomes bare; Squash-with: Task <N> names the partner and doubles as the fixup target.
Consideredkeeping the partner inline and adding fields alongside it. Rejected — the ticket says the field replaces the prose, and one field serving both the guard and the fixup step is simpler than two.

Regression and Baseline degrade to skipped, not failed, when unsupported

regression-baseline-skip-fallbackstatus: active
Chosenskip-not-verified when the project's test command can't target a named test or report a parseable count.
Consideredfailing the run outright. Rejected — this pipeline already trades this way elsewhere (workspace-isolation survivor reports skip rather than fail).

One change, not split into commit-model and mechanical-fields

one-change-not-splitstatus: active
Chosenboth halves ship together.
Consideredshipping commit-per-task first, mechanical fields as a follow-up. The operator chose to do both together.

Open questions

None — every question raised during brainstorming converged to a decision above.
