Why

Once a change reaches FINISHED, nothing captures what the run itself revealed. KAN-23 asks for a retrospective: what problems came up and how the pipeline could avoid them, what drove token/time cost and what would cut it without losing quality, what went well worth repeating, and what could be scripted instead of reasoned through by hand — plus an offer to file actionable findings as Jira issues and a spot for the operator to rate the run.

What changes

Purely additive to /myflow-finish run 2. No new pipeline state, no new command, no state-file schema change.

  • /myflow-finish run 2 gains step 8, immediately after the FINISHED write: a self-review pass.
  • A skip prompt (default: run it) lets the operator opt out per invocation.
  • A new deterministic script, scripts/gather-self-review-context.sh, mechanically collects the SDD ledger, the review-panel record, tasks.md and the relevant git log — no LLM tokens spent scanning for it.
  • One combined reasoning pass — not four separate dispatches — answers all four angles using that bundle plus the live session's own context.
  • Each actionable finding gets its own Jira-filing ask (default: don't file), reusing the existing labelling and never-blocking rules.
  • The operator rates the run 1–5; the rating lives only in the report, never in the state file.
  • The report is written to docs/self-review/<name>-self-review.md, committed and pushed on the base branch.
  • Run 2's terminal handoff gains one line naming the report path and rating, or skipped.

Decisions

Sourced from the brainstorming dialogue. Each is immutable by ID once recorded — a later round supersedes rather than edits.

self-review-placement

Where self-review sits in the pipeline

Chosen: inside /myflow-finish run 2, as step 8, after the FINISHED write — never blocks or delays the archive.

Considered: before the FINISHED write (risks blocking the terminal state); a new standalone /myflow-self-review command (collides with the fixed three-command pipeline surface).

self-review-pass-count

Review structure — one pass vs. four

Chosen: one combined reasoning pass covering all four angles plus the rating.

Considered: four distinct passes mirroring the review panel's separate-lens model — rejected as working against the cost-reduction angle it would itself be auditing.

self-review-context-gathering

Context gathering — script vs. inline reading

Chosen: a new deterministic script assembles the bundle; the reasoning pass only judges it.

Considered: the skill's own prose reading the files itself — rejected, since every run would then re-read and re-summarize the same files from scratch.

self-review-inputs

What the self-review analyzes

Chosen: the preserved artifacts (ledger, panel record, OpenSpec artifacts, archived git history) plus the live session's own context.

Considered: artifacts only, for reproducibility — rejected in favor of the richer signal live context gives for "what went well."

self-review-task-creation

Task creation for findings

Chosen: Jira issues, one filing ask per actionable finding, default No.

Considered: one batched ask covering all findings — less granular control per finding.

self-review-report-storage

Report storage

Chosen: docs/self-review/<name>-self-review.md, committed and pushed.

Considered: the state file only (machine-local, not in git history); both a report and a state-file mirror — dropped once report-only was chosen.

self-review-skip-prompt

Skip prompt semantics

Chosen: fires after FINISHED, never blocks; default answer to "run it?" is Yes.

Considered: none — matched the issue's own phrasing once clarified.

self-review-rating-source

Rating source

Chosen: the operator is asked interactively for the 1–5 rating.

Considered: the agent self-assigning a rating — rejected as a weaker signal than the human who watched the run.

Requirement: Self-review runs only after FINISHED is written

Runs as step 8, immediately after step 7 succeeds, and only then. It cannot prevent, delay, or undo the FINISHED write.

Requirement: A skip prompt defaults to running self-review

Only an explicit No skips. Silence or an unaskable session runs it.

Requirement: Context is gathered deterministically

scripts/gather-self-review-context.sh collects the ledger, panel record, tasks.md and git log without performing any judgement; a missing source is reported and skipped, never fatal.

ScenarioWHEN the change has no review-panel record THEN the script reports it skipped and still returns the other sources, exiting 0

All four angles are answered in a single pass fed the gathered bundle plus live session context.

A finding naming a concrete change gets a filing ask, default No. A filed issue carries the linked issue's labels plus AI-generated.
