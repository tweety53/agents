# KAN-448 — Add a post-guard sanity check and automate the cross-repo spectre link (design)

**Date:** 2026-09-07
**Source:** Jira KAN-448 (Task, Medium) — self-review finding from KAN-423, flow-automation angle;
companion flow-fix issue KAN-439. Approved across two convergence rounds; the second round
revised part 2's placement (decision `link-placement-after-add` below).

## Context and premise

KAN-423's incident: a guard's baseline revert cycle outran a tool timeout, the conductor re-invoked
the guard on top of the stuck revert, and the tree was left with orphaned protective stash entries
— roughly 55 minutes of hand recovery and one wasted conductor dispatch (measured by KAN-442's
proposal quoting KAN-423's self-review; a live incident, not re-runnable).

**KAN-442 already removed the incident's mechanism.** `scripts/check-task-commit-fields.py` no
longer stashes, reverts or resets — its git use is read-only (`diff`, `log`, `rev-parse`) — and
`skills/flow/implement.md` gained a conductor-side inspect-before-retry rule (`git status
--porcelain=v2 --branch` + `git stash list` before re-running a timed-out guard). The ticket's
"revert/reset cycles in particular" premise is therefore partly obsolete. What still mutates a
tree in this repository:

- `scripts/mutate-and-verify.sh` — the review panel's fix-round mutation-proof loop: `git apply`
  → harnesses → `git checkout --` restore. Its EXIT trap re-verifies **only the touched files**
  (residual dirt → exit 3) and there is **no stash-delta check at all**.
- `scripts/prepare-archive-branch.sh` — `git checkout -q $BASE` + `git merge --ff-only` in the
  landing worktree, guarded only by a pre-checkout dirty refusal.

Part 1 delivers the ticket's self-check generically and wires these two; it does not re-implement
what KAN-442 deleted.

Part 2 automates the cross-repo `spectre link`. Today `skills/flow/implement.md` §2 runs it inside
each new worktree after `git worktree add` and makes it explicitly non-gating ("the link is not a
gate"). Peer resolution fails from a worktree, so every cross-repo change logs a refused link and
pays for it at integrate: `check-unfinished-work.sh` reports a false OUTSTANDING verdict that
forces hand verification (KAN-439).

## Part 1 — post-mutation self-check (chosen approach A1)

**New `scripts/lib/post-mutation-check.sh`** — a sourced library, bash 3.2 floor (indexed arrays
only, no associative arrays, per `run-guard-tests.sh`'s own floor):

- `snapshot_tree_state <worktree>` — prints a snapshot: the `git -C <worktree> status
  --porcelain=v2` output, a sentinel line, then `git -C <worktree> stash list`. The caller
  captures it in a variable before its first mutation.
- `check_tree_restored <worktree> <snapshot>` — recomputes both and diffs against the snapshot.
  Every stash entry the snapshot does not hold is printed as `new stash entry: <name>` (the
  ticket's "naming the stash names"); every status line the snapshot does not hold is printed as
  an unexpected status line. Nonzero exit when anything was printed, zero when the tree matches
  the snapshot. **Only new entries are drift** — a stash entry the snapshot recorded and that is
  still present afterwards is expected; a deleted one is not residue the ticket names.
- Both functions are read-only; neither mutates anything.

**Wiring in `scripts/mutate-and-verify.sh`:**

- The snapshot is captured after all refusal paths (steps 3–6) and immediately before step 10's
  `git apply`, so it reflects the exact tree the mutation starts from.
- The EXIT trap keeps its existing order — restore, then the touched-file residual test — and
  runs `check_tree_restored` **after** that test. Touched-file dirt keeps its documented
  **exit 3** (precedence: 3 before 2); broader drift (new stash entries or unexpected status
  lines) forces **exit 2** with the names printed.
- The header's exit-code table gains the second meaning of 2: "post-restore drift detected (new
  stash entries or unexpected status lines named in the output)" alongside "refused before
  mutating anything". Exit 3's contract is unchanged.
- A run killed mid-harness (SIGTERM) still fires the trap: restore runs, the check runs, drift
  exits 2 — the ticket's "caught immediately instead of letting the conductor retry blind."

**Wiring in `scripts/prepare-archive-branch.sh`:** snapshot immediately after the dirty-tree
refusals (tree known clean, branch known), check after `git checkout -q $BASE` and the
`git merge --ff-only` succeed. Drift → stash names printed, exit 2; the header gains the same
exit-2 drift meaning.

**Tests:** new `scripts/test-lib-post-mutation-check.sh` (snapshot/check roundtrip on a clean
tree passes; a planted stash is detected and named; an unexpected status line is detected; a
snapshot-recorded stash still present afterwards is not drift). `scripts/test-mutate-and-verify.sh`
gains: planted stash → exit 2 naming it; touched-file residual together with a planted stash still
exits 3 (precedence). `scripts/test-prepare-archive-branch.sh` gains: planted stash after the
refusal point → exit 2 naming it.

## Part 2 — cross-repo spectre link automation (chosen approach B1, revised placement)

**Evidence, from the shipped spectre code:**

- `spectre/peers` entries are cwd-relative (`gymie ../gymie`); `ResolvePeer`
  (`spectre/internal/tree/peer.go:60`) stats the declared path against the **process working
  directory**. From a worktree, `../gymie` resolves into `.worktrees/` and the link is refused
  ("peer not present") — exactly KAN-439's logged failure. "Peer resolution works from the primary
  checkout" is precisely "peer resolution works when cwd is the primary checkout."
- `spectre link` writes the satellite-side `link.md` under the tree resolved from `--root`
  (default: search upwards from cwd), refusing if that change directory already exists non-empty;
  the peer side requires the canonical change to exist in the peer tree at the cwd-resolved path.
- `check-unfinished-work.sh:252` reads the satellite's own `link.md` **in the worktree** — so a
  link run before `git worktree add` (default root) writes it into the primary tree only; the
  worktree branched from base never contains it and the false OUTSTANDING survives. The ticket's
  literal "before" placement fails the ticket's own goal.

**Mechanism:** in `skills/flow/implement.md` §2 (isolate-workspace), after each additional
worktree's `git worktree add`, run, as one step: `cd <that repo's primary checkout>` then
`spectre link --root <worktree>/spectre <canonical-peer>:<name>`. cwd performs peer resolution;
`--root` places the satellite-side `link.md` inside the worktree. A refusal is a **hard stage
failure**: report and stop the run. The paragraph's "A failure is reported and the run continues:
the link is not a gate" sentence is deleted. A change with one worktree runs nothing here
(unchanged); the canonical worktree's own creation carries no link — the canonical change
directory is the link's anchor, not a consumer.

**Recorded consequences:** the peer-side write (`## Parts` / `## Merge order`) lands in the
canonical repo's primary tree at the path its peers entry declares, and is that project's to
commit by its own convention. The satellite-side `link.md` inside the worktree is committed there
per `skills/flow-contracts/git-boundaries.md`'s existing `link.md` carve-out, unchanged.

**KAN-439** is resolved by this part (its own first-named fix) and is closed when this change
lands; `check-unfinished-work.sh` is not touched.
