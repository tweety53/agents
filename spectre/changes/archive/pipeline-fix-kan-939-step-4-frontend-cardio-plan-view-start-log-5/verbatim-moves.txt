A `VISUAL-VERIFY-MISSING:` line means a UI-path commit landed after the last HEAD a verifier saw — a visual-fix task's, a panel fix's, a full-suite fix's or a fix run's own.
A landing HEAD whose UI no visual verifier saw is such a finding, never a risk line.

The one other pass is an operator who hand-verified that HEAD's UI and calls the verdict wrong: record it with `flow record verdict false-positive -change <name> -guard check-visual-verify-dispatched -reason "<the operator's reason, verbatim>" -C <canonical-worktree>` right after the stop, and re-run `prepare`.
The command flags the guard's newest verdict, and `prepare` stops at the first `MISSING` worktree so that row is the newest; `prepare` passes only on a flag on that worktree's own row whose verdict names its current HEAD (`— HEAD <sha>`), so a later commit or a rebase needs a new verifier or a new flag.
A flag made at `prepare` does not carry to `land`: the reshape and the archive move HEAD, so `land` stops again and the operator flags that HEAD anew.
The gate runs on an archived re-run with no new work too, again on each worktree a base move rebases in `prepare`, before every push `commit` and `land` make on every route — `land`'s stop names the worktrees already pushed — and again after a re-sync on a rejected push.
So the gate covers every push the pipeline makes, and the forge merge of an opened PR is of the verified head; run 2 `cleanup` adds no check, since it could only report after landing.
