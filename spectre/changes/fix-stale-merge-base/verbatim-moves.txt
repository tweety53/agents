# Self-review fix: a carried CLEAR names the actual merge base, which becomes <rebased-merge-base> for the run.
Run `reshape-branch.sh <abs-worktree> <name> <recorded-merge-base>`, where `<recorded-merge-base>` is the merge base recorded in the state file's `worktrees` map for this worktree — the same merge base **Resolving a change's worktrees** and the finish-preflight verdict above both reference — **or `<rebased-merge-base>`, for a worktree **Sync the branch onto the base** (`skills/flow/sync-onto-base.md`) rebased**.
`<recorded-merge-base>` is the merge base recorded in the state file's `worktrees` map for this worktree — **or `<rebased-merge-base>` from step 2 above, for a worktree this run rebased**, never the state file's now-stale pre-rebase value for that worktree.
A `CLEAR` naming `merge base now <sha>` makes that `<sha>` the worktree's `<rebased-merge-base>` for the rest of this run, exactly as a clean sync's does.
`<recorded-merge-base>` is the merge base recorded in the state file's `worktrees` map for this worktree — **or `<rebased-merge-base>` from step 2 above, for a worktree this run rebased or whose `CLEAR` named `merge base now <sha>`**, never the state file's now-stale pre-rebase value for that worktree.
**Then run `check-visual-verify-dispatched.sh <worktree> <change-name> <recorded-merge-base>`**, once per worktree in the same resolved set, `<recorded-merge-base>` being the same state-file value the preflight above already reads.
Then run `check-visual-verify-dispatched.sh <worktree> <name> <recorded-merge-base>` once per worktree in the same set, per **Run 1 — the branch is not merged** (`skills/flow-contracts/finish-contract-run1.md`): `VISUAL-VERIFY-OK:` joins `CLEAR:`; `VISUAL-VERIFY-MISSING:` and an exit 2 take the `OUTSTANDING:` and stop-and-ask rows below.
When this same repository is also declared in `## apps`, its root follows that table's own rule — **Roots in `## apps` are main checkouts** above — resolving to the change's apply worktree there rather than the main checkout; a `regression checkout` with no matching `## apps` row has no worktree to resolve and is always the main checkout.
**Then run `check-visual-verify-dispatched.sh <worktree> <change-name> $(git -C <worktree> merge-base HEAD origin/$BASE)`**, once per worktree in the same resolved set — the fork point itself, because this runs before the base-moved check below can name a rebased one, and the state-file value is stale after an earlier rebase.
When this same repository is also declared in `## apps`, its root follows that table's own rule — **Roots in `## apps` are main checkouts** above — resolving to the change's apply worktree there rather than the main checkout; a `regression checkout` with no matching `## apps` row resolves the same way — to a worktree of that repository on the change's branch when one exists, otherwise the main checkout.
